    7. Database Access

    The following chapters round out the course by covering database access from TypeScript scripts, drawing inspiration from the chapters “Using the MySQL DBMS” and “Using the SQLAlchemy ORM” in the course “Introduction to Python 3 and the Flask Framework” (2019). Three approaches are presented in succession: direct access to the DBMS using the native mysql2 driver, followed by two ORM (object-relational mapping) approaches—TypeORM and Prisma.

    7.1. Direct Access to the Database

    Two SQL scripts, provided with this chapter, allow you to create the test databases: dbpersons (a single table, used in the chapter on the native driver) and dbschool (four interconnected tables, used in the two chapters on ORM).

    // databases/mysql/mysql-02.ts
// In this new script, the database connection is isolated in a function.
// Ports the Python script [mysql_02].
import mysql from 'mysql2/promise';

// connects then disconnects (login, pwd) from database [database] on server [host]
// throws an exception if there is a problem
async function connect(host: string, database: string, login: string, pwd: string): Promise<void> {
  let cnx: mysql.Connection | undefined;
  try {
    // connection
    cnx = await mysql.createConnection({ host, user: login, password: pwd, database });
    console.log(
      `Successful connection to database=${database}, host=${host} as user=${login}, passwd=${pwd}`,
    );
  } finally {
    // close the connection if it was opened
    if (cnx) {
      await cnx.end();
      console.log('Successful disconnection\n');
    }
  }
}

// ---------------------------------------------- main
// connection credentials
const USER = 'admpersons';
const PASSWD = 'nobody';
const HOST = 'localhost';
const DATABASE = 'dbpersons';

// connection of an existing user
try {
  await connect(HOST, DATABASE, USER, PASSWD);
} catch (error) {
  // display the error
  console.log(String(error));
}

// connection of a non-existent user
try {
  await connect(HOST, DATABASE, 'xx', 'xx');
} catch (error) {
  // display the error
  console.log(String(error));
}

    Let’s comment on this code:

    • line 9: [async function connect(host, database, login, pwd): Promise<void>] — an async function that returns nothing but can raise an exception — it does not catch connection errors itself; instead, it lets them propagate to the caller;
    • line 40: [await connect(HOST, DATABASE, 'xx', 'xx')] — the second call, with a user “xx” who does not exist on the MySQL side, raises an exception that the enclosing catch block displays.

    Version-specific issue: On a recent MySQL server (8.4 and later), this second call may produce a different message: "Error: Plugin 'mysql_native_password' is not loaded" instead of "Access denied for user 'xx'@'localhost'." The cause is unrelated to the script: to avoid revealing whether an account exists or not (anti-enumeration protection), MySQL simulates an authentication exchange when logging in with an unknown user—and this simulation is hardcoded to use the legacy plugin mysql_native_password, which has been disabled by default since MySQL 8.4. The principle demonstrated by this script (an exception thrown and intercepted on invalid credentials) remains intact; to restore the exact message displayed, add `mysql_native_password=ON` below `[mysqld]` in the server’s `my.ini` file, then restart the server.

    // databases/mysql/mysql-module.ts
// Reusable functions to execute a list (or a file) of SQL commands
// on an open MySQL connection. Ports the Python module [mysql_module].
import type { Connection, FieldPacket, ResultSetHeader, RowDataPacket } from 'mysql2/promise';
import { readFile } from 'node:fs/promises';

// displays the result of an SQL command (result of a mysql2 query())
// - if there is a [fields] array, it was a SELECT: we display the columns
//   then the rows;
// - otherwise, it was an update statement (INSERT/UPDATE/DELETE/DDL): we
//   display the number of modified rows (equivalent of cursor.rowcount).
function displayInfo(rows: RowDataPacket[] | ResultSetHeader, fields: FieldPacket[] | undefined): void {
  if (fields && fields.length > 0) {
    // it was a SELECT — fields describes the requested columns
    const titles = fields.map((f) => f.name);
    console.log(titles.join(', '));
    console.log('*'.repeat(titles.join(', ').length));
    for (const row of rows as RowDataPacket[]) {
      console.log(titles.map((t) => row[t]));
    }
    console.log('*'.repeat(titles.join(', ').length));
  } else {
    // no columns described — update statement
    const header = rows as ResultSetHeader;
    console.log(`number of modified rows: ${header.affectedRows}`);
  }
}

// uses the open connection [connection]
// executes on this connection the SQL commands contained in the list [sqlCommands]
// (one command per element; empty lines or lines starting with # are ignored)
// - if verbose=true, each execution of an SQL statement is followed by a display
//   indicating its success or failure;
// - if stop=true, the function stops at the 1st error encountered, otherwise
//   it executes all the commands;
// - if withTransaction=true, any error cancels all the SQL statements
//   executed before (rollback); otherwise each command is committed
//   independently (default behaviour of mysql2);
// the function returns an array [error1, error2, ...]
export async function executeListOfCommands(
  connection: Connection,
  sqlCommands: string[],
  verbose = false,
  stop = true,
  withTransaction = true,
): Promise<string[]> {
  const errors: string[] = [];
  if (withTransaction) {
    await connection.beginTransaction();
  }
  try {
    for (const rawCommand of sqlCommands) {
      // remove the leading and trailing blanks of the current command
      const command = rawCommand.trim();
      // empty command or comment? move on to the next one
      if (command === '' || command[0] === '#') {
        continue;
      }
      // execution of the current command
      try {
        const [rows, fields] = await connection.query(command);
        // no error
        if (verbose) {
          console.log(`[${command}]: Successful execution`);
        }
        displayInfo(rows as RowDataPacket[], fields);
      } catch (error) {
        const msg = `${command}: Error (${error})`;
        errors.push(msg);
        if (verbose) {
          console.log(msg);
        }
        // do we stop?
        if (withTransaction || stop) {
          return errors;
        }
      }
    }
    return errors;
  } finally {
    // commit / roll back the transaction if there is one
    if (withTransaction) {
      if (errors.length > 0) {
        await connection.rollback();
      } else {
        await connection.commit();
      }
    }
  }
}

// uses the open connection [connection]
// executes on this connection the SQL commands contained in the
// text file [sqlFilename] (one command per line)
export async function executeFileOfCommands(
  connection: Connection,
  sqlFilename: string,
  verbose = false,
  stop = true,
  withTransaction = true,
): Promise<string[]> {
  try {
    const content = await readFile(sqlFilename, 'utf-8');
    return await executeListOfCommands(connection, content.split('\n'), verbose, stop, withTransaction);
  } catch (error) {
    return [`The file ${sqlFilename} could not be processed: ${error}`];
  }
}

    Let’s comment on this code:

    • line 45: [if (withTransaction) { await connection.beginTransaction(); }] — mysql2 is in AUTOCOMMIT mode by default (each query is validated individually) — beginTransaction() explicitly switches the connection to transactional mode, just as connexion.start_transaction() would on the Python side;
    • line 76: [if (withTransaction || stop) { return errors; }] — in transactional mode, the first error immediately terminates the loop — continuing would be pointless since the entire transaction will be rolled back anyway;
    • line 82: [if (errors.length > 0) { await connection.rollback(); } else { await connection.commit(); }] — global commit or rollback, depending on whether an error occurred or not — see, however, the pitfall noted in the [mysql-04] script below.

// Main script: executes the SQL commands file [data/commands.sql],
// with or without a transaction depending on the command-line parameter.
// Ports the Python script [mysql_04].
//   npx tsx databases/mysql/mysql-04.ts true   (with transaction)
//   npx tsx databases/mysql/mysql-04.ts false  (without transaction)
import mysql from 'mysql2/promise';
import { configure } from './config-04.js';
import { executeFileOfCommands } from './mysql-module.js';

const config = configure();

// ---------------------------------------------- main
// checking the call syntax
const args = process.argv.slice(2);
let error = args.length !== 1;
let withTransactionText = '';
if (!error) {
  withTransactionText = args[0].toLowerCase();
  error = withTransactionText !== 'true' && withTransactionText !== 'false';
}
if (error) {
  console.log('syntax: mysql-04.ts true / false');
  process.exit(1);
}

// computing a text
const withTransaction = withTransactionText === 'true';
const text = withTransaction ? 'with transaction' : 'without transaction';

// screen logs
console.log('--------------------------------------------------------------------');
console.log(`Executing the SQL file ${config.commandsFilename} ${text}`);
console.log('--------------------------------------------------------------------');

// execution of the SQL statements of the file
let connection: mysql.Connection | undefined;
let errors: string[] = [];
try {
  // connection to the database
  connection = await mysql.createConnection({
    host: config.host,
    user: config.user,
    password: config.password,
    database: config.database,
  });
  // execution of the SQL commands file
  errors = await executeFileOfCommands(connection, config.commandsFilename, true, false, withTransaction);
} catch (fatalError) {
  console.log(`The following fatal error occurred: ${fatalError}`);
  process.exit(1);
} finally {
  if (connection) {
    await connection.end();
  }
}

// display of the number of errors
console.log('--------------------------------------------------------------------');
console.log('Execution completed');
console.log('--------------------------------------------------------------------');
console.log(`There were ${errors.length} error(s)`);
for (const currentError of errors) {
  console.log(currentError);
}

    Caution: You might expect the `persons` table to be empty after this `rollback()`—that’s what the original Python course on SQLAlchemy incorrectly states. In reality, with MySQL/MariaDB (as with most DBMSs), the data definition statements (DDL: CREATE TABLE, DROP TABLE...) implicitly commit and roll back any ongoing transactions before executing. Here, the CREATE and TABLE from the second command have therefore already (invisibly) committed everything that came before, including—since there was nothing before it—themselves; the two INSERT commands that follow then, in effect, open a new implicit transaction, which will indeed be rolled back... except that, in practice, checking the database shows that the two inserted rows remain present after the rollback(): the CREATE TABLE committed the transaction while the loop was still running, even before the subsequent INSERT statements were executed—these, too, are therefore permanently committed as soon as they are executed, outside of any explicit transaction. Remember the general rule: a DDL cannot be rolled back by a ROLLBACK, and it silently commits any transaction that was open before it.

// Parameterized queries: single prepared insertion, then bulk insertion.
// Ports the Python script [mysql_05]. Here we recreate the [persons] table with
// the schema having an [id] column (as in script mysql-03), so that this script
// is independent of the state left by mysql-04.
import mysql from 'mysql2/promise';

// the user's identity
const ID = 'admpersons';
const PWD = 'nobody';
// the DBMS host machine
const HOST = 'localhost';
// identity of the database
const DATABASE = 'dbpersons';

type Person = [id: number, lastName: string, firstName: string, age: number];

// list of persons (id, lastName, firstName, age)
const persons: Person[] = [];
for (let i = 0; i < 5; i++) {
  persons.push([i, `l0${i}`, `f0${i}`, i + 10]);
}
persons.push([40, "d'Aboot", "Y'éna", 18]);

// another list of persons
const otherPersons: Person[] = [];
for (let i = 0; i < 5; i++) {
  otherPersons.push([i + 100, `l1${i}`, `f1${i}`, i + 20]);
}
otherPersons.push([200, "d'Aboot", "F'ilhem", 34]);

// access to the DBMS
let connection: mysql.Connection | undefined;
try {
  // connection
  connection = await mysql.createConnection({ host: HOST, user: ID, password: PWD, database: DATABASE });

  // (re)creation of the table with the [id]-column schema (see mysql-03.ts)
  await connection.query('drop table if exists persons');
  await connection.query(
    'create table persons (id int PRIMARY KEY, first_name varchar(30) NOT NULL, last_name varchar(30) NOT NULL, ' +
      'age integer NOT NULL, unique(last_name,first_name))',
  );

  // deletion of the existing records
  await connection.query('delete from persons');
  // person-by-person insertions with a prepared statement
  for (const person of persons) {
    const [id, lastName, firstName, age] = person;
    await connection.execute('insert into persons(id,last_name,first_name,age) values(?,?,?,?)', [id, lastName, firstName, age]);
  }
  // bulk insertion of a list of persons — equivalent of executemany:
  // mysql2 offers connection.query('insert ... values ?', [[...],[...],...])
  // which builds a single multi-row query
  const values = otherPersons.map(([id, lastName, firstName, age]) => [id, lastName, firstName, age]);
  await connection.query('insert into persons(id,last_name,first_name,age) values ?', [values]);

  // committing the transaction — here each query has already been auto-committed
  // (mysql2 is in AUTOCOMMIT mode by default, like the default mode mentioned in
  // script mysql-03; so there is nothing to commit explicitly)
  console.log(`${persons.length + otherPersons.length} persons inserted.`);
} catch (error) {
  console.log(`The following error occurred: ${error}`);
} finally {
  if (connection) {
    await connection.end();
  }
}

    7.1.8. Conclusion

    The native mysql2 driver provides direct, straightforward access to the DBMS: you write the SQL yourself, manage transactions yourself, and the result of a query is a simple array of rows JavaScript. This is the same approach as that of the Python module mysql.connector used in Chapter 16 of the Python/Flask course.     7.2. Using the TypeORM ORM

    We will now discuss ORM, drawing on the chapter “Using the SQLAlchemy ORM” (Chapter 19) from the Python/Flask course. The principle behind ORM (object-relational mapping) is to manipulate language objects rather than writing SQL: a class corresponds to a table, an instance to a row, an attribute to a column, and a relationship between classes (association, composition) to a foreign key.

    Two ORM implementations are presented one after the other, using the same example, so they can be compared: TypeORM in this chapter, followed by Prisma in the next chapter. Of the two, TypeORM is the one whose style most closely resembles SQLAlchemy (decorated classes, Repository queried using methods); Prisma, on the other hand, generates a fully typed client from a separate declarative schema file.

// Computes, for a given student, their average weighted by the coefficients of
// the subjects, as well as their min and max grade. Ports the Python script
// [main_stats_for_student] (chapter 19, scripts 05).
//
// Pitfall to know: the `decimal` columns (here `grade.value` and
// `subject.coefficient`) are typed `number` on the TypeScript side in
// the entity, but the mysql2 driver actually returns them as
// *character strings* (so as not to lose precision by
// converting them to a floating-point `number`). `typeof grade.value` is `'string'`
// at runtime, despite the declared type. A computation such as
// `sum += grade.value * subject.coefficient` would then perform a
// concatenation or a risky implicit conversion: you must convert
// explicitly with `Number(...)` before any computation.
import { AppDataSource } from './data-source-school.js';
import { Student } from './entities/student.entity.js';

// computes the statistics (weighted average, min, max) of a student
async function studentStats(studentId: number): Promise<void> {
  const studentRepo = AppDataSource.getRepository(Student);
  // we load the student with their grades and, for each grade, the associated
  // subject (to have the coefficient) — a single query with two
  // joins, thanks to the nested `relations` option
  const student = await studentRepo.findOneOrFail({
    where: { id: studentId },
    relations: { grades: { subject: true } },
  });

  console.log(`Statistics of student {"id":${student.id},"lastName":"${student.lastName}","firstName":"${student.firstName}"}`);

  if (student.grades.length === 0) {
    console.log('  no grades.');
    return;
  }

  let weightedSum = 0;
  let coefficientsSum = 0;
  let min = Number.POSITIVE_INFINITY;
  let max = Number.NEGATIVE_INFINITY;

  for (const grade of student.grades) {
    // explicit conversion: `grade.value` and `grade.subject.coefficient`
    // are strings at runtime despite their declared type `number`
    const value = Number(grade.value);
    const coefficient = Number(grade.subject.coefficient);
    weightedSum += value * coefficient;
    coefficientsSum += coefficient;
    min = Math.min(min, value);
    max = Math.max(max, value);
    console.log(`  grade=${value.toFixed(2)} subject="${grade.subject.name}" (coefficient ${coefficient.toFixed(2)})`);
  }

  const average = weightedSum / coefficientsSum;
  console.log(`  weighted average=${average.toFixed(2)}, min=${min.toFixed(2)}, max=${max.toFixed(2)}`);
}

try {
  // student id=11: grades subject1=10 (coef 1.0), subject2=6 (coef 2.0)

  await studentStats(11);
  console.log();
  // student id=21: grades subject1=12 (coef 1.0), subject2=8 (coef 2.0)
  await studentStats(21);
  console.log();

}

    7.2.7. Conclusion

    TypeORM allows you to write read/write operations without SQL, using decorated entities similar in spirit to SQLAlchemy—at the cost of a significant design difference to be aware of (no implicit lazy loading of relationships: any relationships not explicitly requested are omitted) and a tooling pitfall specific to TSX execution (column types must be specified explicitly). The following chapter uses the exact same example with Prisma to compare the two approaches.

    7.3. Using the Prisma ORM

    Second ORM, using the same example as the previous chapter (the dbpersons and dbschool databases), to compare the two approaches. Prisma differs from TypeORM in its design: instead of annotating classes, the database schema is described in a separate file using Prisma’s own declarative format, from which the prisma generate command generates a fully typed client.

    Important: As of the writing of this chapter, Prisma ORM is at version 7, which has undergone significant internal changes compared to previous versions (5 and 6): the query engine, previously a separately downloaded binary compiled in Rust, is now a WebAssembly module embedded directly in the npm package, combined with a driver adapter (here @prisma/adapter-mariadb) that relays queries to a traditional JavaScript driver. The general principle, however, remains the same as with previous versions of Prisma, and the following therefore applies to those versions as well.
    Note on this environment: the `npx prisma generate` command, which generates the TypeScript client from the schema.prisma file, requires a Prisma-specific network resource (binaries.prisma.sh) to retrieve an internal component from its CLI—a resource that the network policy of the runtime environment used to prepare this course did not allow access to. The scripts in this chapter were therefore written and reviewed with the same care as the previous ones, but could not be executed or verified in this environment—unlike those in the two previous chapters, all of which were executed and their results verified. On a machine with normal Internet access (the typical case), `npx prisma generate` runs without any particular issues, and the scripts should produce the “expected” outputs shown below, calculated from the same data already verified in the previous chapter.

// the subjects, as well as their min and max grade. Uses the same example as
// databases/typeorm/typeorm-04-stats.ts.
//
// Pitfall to know, different from TypeORM's: Prisma does not return
// the `Decimal` columns (here `grade.value` and `subject.coefficient`) as
// strings, but as instances of the `Prisma.Decimal` class
// (provided by the decimal.js library), so as not to lose any
// decimal precision. `typeof grade.value` is `'object'`, not `'number'`
// nor `'string'`. A computation such as `grade.value * subject.coefficient`

// computes the statistics (weighted average, min, max) of a student
async function studentStats(studentId: number): Promise<void> {
  // a single query, with two levels of join (grades, then the subject of
  // each grade) to have the coefficient of each subject
  const student = await prisma.student.findUniqueOrThrow({
    where: { id: studentId },
    include: { grades: { include: { subject: true } } },
  });

  console.log(`Statistics of student {"id":${student.id},"lastName":"${student.lastName}","firstName":"${student.firstName}"}`);

  if (student.grades.length === 0) {
    console.log('  no grades.');
    return;
  }

  let weightedSum = 0;
  let coefficientsSum = 0;
  let min = Number.POSITIVE_INFINITY;
  let max = Number.NEGATIVE_INFINITY;

  for (const grade of student.grades) {
    // explicit conversion: `grade.value` and `grade.subject.coefficient`
    // are `Prisma.Decimal` values, not `number` values
    const value = grade.value.toNumber();
    const coefficient = grade.subject.coefficient.toNumber();
    weightedSum += value * coefficient;
    coefficientsSum += coefficient;
    min = Math.min(min, value);
    max = Math.max(max, value);
    console.log(`  grade=${value.toFixed(2)} subject="${grade.subject.name}" (coefficient ${coefficient.toFixed(2)})`);
  }

  const average = weightedSum / coefficientsSum;
  console.log(`  weighted average=${average.toFixed(2)}, min=${min.toFixed(2)}, max=${max.toFixed(2)}`);
}

  await studentStats(11);
  console.log();
  await studentStats(21);
  console.log();
  await studentStats(32);
  console.log();
  await studentStats(42);
} finally {
  await prisma.$disconnect();
}

    7.3.6. Conclusion

    Using the same example, TypeORM and Prisma produce code of comparable length and readability—the differences are mainly stylistic: decorated classes and a Repository for TypeORM (more similar to SQLAlchemy and Spring Data JPA), and a separate declarative schema and fully generated client for Prisma (more similar in spirit to a tool like Alembic combined with a code generator). Both avoid writing SQL, and both share the same design choice—no implicit lazy loading of relationships—which sets them apart from SQLAlchemy. The choice between the two, in a real-world project, comes down mainly to the ecosystem (Prisma Studio, Prisma migrations, etc.) and the team’s preferences.
